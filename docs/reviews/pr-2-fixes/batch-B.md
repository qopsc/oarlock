## 2a. Rework after review (commits 6d076079, ef548a36, 9508b6e1, 1efd7c3a, a116a519)

- S-01 rework (6d076079; superseded in part by 2b): workspace roots no longer enter Tauri's asset scope. They live in `Access` (`asset_scope.rs`), which only `oarlock-asset` reads; Tauri's scope holds the font faces `system_font_faces` grants (and forbids the app-state folders). `asset:` and `https://asset.localhost` are out of `frame-src`; `contentSecurityPolicy.test.ts` checks `asset://` is not framable and the two sources are absent. A workspace file is unreachable through `asset:` structurally, since nothing but `grant_file` writes to that scope.
- S-05 rework (same commit, it shares the code): the pre-open judgement is `Access::may_open`. `..` is refused; a name under a root is passed to the post-open check; with all folders allowed only dot names are turned away; otherwise the name's folder is resolved once and judged (so `~/code` to a volume and macOS `/tmp` work). The production wiring (`may_open`, `serves_opened`) is what `protocol()` builds its closures from, and `a_workspace_file_reached_through_a_link_is_served_by_the_production_judgements` runs `respond_with` on it with a link-spelled root. The only filesystem touch before the open is that one folder resolution, for names not already under a root while the switch is off.
- Low, same commit: refusals (`status_only`) carry `nosniff` and the sandbox CSP; the busy 503 carries `Retry-After` and the app origin; `rustfmt` run on `asset_all_folders.rs` and its tests.
- S-03 rework (ef548a36): `NATIVE_FILES` now holds `oarlock-ai-sessions.before-message-files.json` and `secrets.json`, so the wrapper and `refuse_write` refuse both; the T-02 test iterates the list.
- S-04 rework (9508b6e1): `plugin:resources|close` is not a store command, so the wrapper cannot see it. `core:resources:deny-close` is added to `capabilities/default.json` (no frontend code closes a resource) with a test.
- S-12 rework (1efd7c3a): the first save of each store per run removes `.<name>.<pid>.<n>.tmp` files of another process; doc comment and test renamed (`a_save_refuses_a_link_and_leaves_its_target_alone`); both `secure_file.rs` copies still identical.

## 2b. Second rework (commit 51dc7b6f, subject S-01 rework; it also carries the S-05 rework, the code is shared)

- S-01: Tauri's `asset:` protocol cannot be switched off from here (`assetProtocol.enable: false` fails tauri-build, which requires the `protocol-asset` feature in `Cargo.toml` to match, and `Cargo.toml` is off limits). So its scope is made to match nothing: `install` forbids every filesystem root (`/`, or each drive letter, the verbatim form and `\\` on Windows), and a forbidden pattern beats any allowed one, including the folders the dialog plugin grants on Open Folder. The allow list stays empty and the former font and workspace grants are gone. Font faces load through `oarlock-asset`: `system_font_faces` grants each face file to `Access` (`grant_file`), the handler allows `font/*`, `application/font-*` and `application/x-font-*` (what `infer` returns for woff, woff2, ttf and otf), `fontFeatures.ts` builds the URL with `assetSrc` plus the page token, and `tauri.conf.json` has no `asset:` source in `img-src`, `media-src`, `font-src` or `frame-src` (fonts use `oarlock-asset:` in `font-src`). Tests: `tauris_asset_scope_matches_nothing_whatever_the_dialog_grants` (the forbid patterns match a picked folder's file; the allow list is empty), `a_granted_font_face_is_served_as_a_font_and_nothing_beside_it`, `font_faces_are_served_by_their_exact_file_only`, and the CSP tests (`names no source of Tauri's asset protocol...`, img/media/font allow the guarded scheme). Not tested: a real `Scope::is_allowed` call, since a Tauri `Scope` cannot be built in a unit test here; the test checks the patterns `forbid_directory` adds against the glob options Tauri uses. On Windows `frame-src http:` still matches `http://asset.localhost`, but nothing is served there.
- S-05: `Access::may_open` makes no filesystem call. A granted root is stored under its authorized spelling and its resolved one (`grant_root` resolves it once, when the registry authorizes it), fonts likewise; a request is judged by name, and the opened handle is judged again. `a_name_through_a_link_matches_a_root_kept_under_both_spellings` runs with no resolver and includes `/net/host/share` and a nonexistent folder (refused by name); `granting_a_link_spelled_root_records_where_it_resolves` uses a real link; the production-wiring test now grants the link-spelled root.
- Noted, not changed (Opus Lows): DNS eviction uses `try_lock`, so it can evict a slot whose `Arc` a caller already cloned, and two lookups of one host can briefly overlap (an `Arc::strong_count == 1` check would close it). The staging sweep in `secure_file.rs` assumes single-instance keeps one process per profile.

## 2c. Dot-folder gap (final targeted round)

- S-01: `forbid_directory("/", true)` stores `/**`, and the scope's `requireLiteralLeadingDot` keeps `**` out of any part starting with a dot, so a folder the dialog plugin allows at or below one (`~/.config/proj`, `~/.dotfiles`, `~/.local/src/app`) was still served by `asset:`. `install` now listens on Tauri's asset scope and, for every `Event::PathAllowed(path)`, calls `forbid_directory(path, true)` and `forbid_file(path)`; the pattern made from the allowed path names the dot part literally, so it matches. The root forbids stay. `on_scope_event` is the handler, tested on its own: `tauris_asset_scope_matches_nothing_whatever_the_dialog_grants` now shows the root forbids alone miss the three dot-named folders, that the handler forbids exactly the allowed path, that the resulting pattern matches files and subfolders under it with Tauri's match options, and that `PathForbidden` events do nothing. Limitation: a Tauri `Scope` cannot be built in a unit test, so the `listen` registration itself and a real `Scope::is_allowed` call are not exercised.
- Deferred, unverified: the Windows forbid list (drive letters, `\\?\X:\`, `\\`) has not been run on Windows; the listener covers whatever the dialog plugin allows there.

## 2d. Links inside a workspace (Mythos round 1, S-05 residual)

- A link in a workspace can point anywhere (`logo.png -> /net/attacker.example/share/x`), and `open_preview` follows it before the opened file can be judged. `Access::may_open_following` now walks the requested name's prefixes with `read_link` alone (no stat, no open), composes each link's target text with the rest of the name, folds `.` and `..` by name (`flatten`), and requires the composed name to pass `may_open` too, repeating for links in the composed name. A link that composes outside every root or `..` past the start, a loop, more than 40 links, and an unreadable link (permission denied) are refused before any open; a link that composes inside a root, a link-spelled root (`/tmp` to `/private/tmp`) and the canonical spelling are still served. `may_open` in `asset_all_folders.rs` uses it with `std::fs::read_link`. With "access all folders" on, any non-dot name passes by design, so a link to a share is allowed there.
- Tests: `a_link_is_followed_by_name_and_must_stay_inside_a_root` (injected link reader: inside, back-into-root, climbing out, network share, folder link out, loop; names outside the root are never read), `flattening_folds_dots_and_refuses_to_climb_past_the_start`, and `a_workspace_link_to_an_outside_target_is_refused_before_anything_is_opened` (real links, one to a missing outside folder and one to an existing outside file, through `respond_with`; the post-open closure records that nothing was opened, and a link staying inside is served).
- Limit: the walk reads each prefix once per pass, so a hostile directory can race a link into place between the read and the open; the post-open handle check still catches what it resolves to, but the side effect of that open is not prevented against a concurrent writer.
